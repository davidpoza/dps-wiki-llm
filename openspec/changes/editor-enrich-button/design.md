## Context

The Explorer editor has several toolbar actions (save, sync, link discovery, versions, PDF export). Notes created manually or imported outside the ingest pipeline lack the `## Summary` section and frontmatter `keywords` generated by `SourceNoteLlmService`. The existing `source-note-system` prompt already defines the contract for extracting summary and keywords from a note body.

Key constraints:
- `SourceNoteLlmService.clean()` is tightly coupled to ingest (`NormalizedSourcePayload`, `LlmSourceNote`); reusing it directly in this context would create inappropriate coupling.
- The LLM call can take several seconds; the UI must show a loading state.
- The frontend already tracks frontmatter separately from body content; the enrich result can be applied without re-parsing the full file.

## Goals / Non-Goals

**Goals:**
- One-click LLM enrichment of the currently open note from the editor toolbar.
- Apply `keywords` to frontmatter and inject `## Summary` section into body if absent.
- Reuse the `source-note-system` prompt without modifying it.
- Keep the user in control: result is applied as a dirty edit, not auto-saved.

**Non-Goals:**
- Updating/replacing an existing `## Summary` section (idempotent on summary).
- Batch enrichment of multiple notes.
- Adding a dedicated prompt key for enrich (reuses `source-note-system`).
- Streaming the LLM response.

## Decisions

### 1. Backend: new endpoint in `FileController`, not a separate controller

`POST /api/files/enrich?path=<path>` — reads the file from disk, calls the LLM, returns `EnrichResultDto { summary, keywords }`.

**Rationale**: The operation is file-path-centric, consistent with existing `FileController` endpoints. A separate controller adds a layer with no benefit at this scope.

**Alternative considered**: Accepting file content in the request body (avoiding a disk read). Rejected because the backend is the source of truth for file content and the frontend content may be unsaved/dirty; we want to enrich the persisted version, not an intermediate draft.

### 2. New `NoteEnrichService` rather than reusing `SourceNoteLlmService.clean()`

`NoteEnrichService.enrich(String content)` calls the LLM via `PromptService.getText("source-note-system")` and extracts only `summary` + `keywords`.

**Rationale**: `SourceNoteLlmService` is shaped around the ingest domain (`NormalizedSourcePayload`, `LlmSourceNote`, `raw_context`, `extracted_claims`, `open_questions`). The enrich use case only needs summary and keywords, and coupling the editor path to ingest internals would make both harder to evolve independently.

**Alternative considered**: Adding an `enrich()` overload to `SourceNoteLlmService`. Rejected because that class already handles enough and the result type mismatch would require nullable fields or a union return type.

### 3. Frontend applies result to in-memory editor state, not by reloading from disk

After receiving `{ summary, keywords }`:
1. Update `frontmatter` signal (merges/replaces `keywords` key).
2. If the current body (obtained from `currentMarkdown`) does not contain a heading matching `## Summary` (case-insensitive), prepend `## Summary\n\n{summary}\n\n` to the body.
3. Call `editor.action(replaceAll(newBody))` and mark the editor dirty.

**Rationale**: Follows the same pattern used by `restoreVersion()` — mutate in-memory state, mark dirty. No file system round-trip needed. The user can review and discard the change if unwanted.

**Alternative considered**: Saving to disk immediately after enriching. Rejected because it removes the review step and diverges from the expected UX of the other toolbar actions.

### 4. Summary injection position: immediately after frontmatter (start of body)

If no `## Summary` heading is found, inject `## Summary\n\n{summary}\n\n` at the start of `currentMarkdown`.

**Rationale**: Summary is a structural overview; placing it at the top is conventional for knowledge-base notes. Detecting "no existing summary" via a heading search on the body string is simple and reliable.

## Risks / Trade-offs

- **LLM latency (3–15 s)** → Button shows loading spinner; disabled while in-flight. Toast on error.
- **Source-note-system prompt may include fields (raw_context, extracted_claims) not needed here** → `NoteEnrichService` ignores those fields; parsing only summary + keywords. Validation only checks those two fields are present.
- **Enriching a dirty (unsaved) note** → The endpoint reads from disk, so unsaved edits are not sent to the LLM. A future iteration could accept body content in the request if needed. For now this is documented behavior.
- **Frontmatter keywords replacement** → Existing manually curated keywords are overwritten. This is intentional (LLM output is authoritative for this field) but should be visible to the user in the dirty diff before saving.

## Migration Plan

No database changes. No existing behavior is modified. Feature is additive:
1. Deploy backend with new `NoteEnrichService`, `EnrichResultDto`, and `FileController#enrich` endpoint.
2. Deploy frontend with new button and `ApiService#enrichNote`.
3. Rollback: remove the endpoint and the button independently; no data migration needed.
